# Karpathy编码行为准则

**核心原则：** 此准则偏向谨慎而非速度。简单任务，请自行判断。

## 1. 编码前思考

**勿假设。勿藏困惑。明权衡。**

实现的前：

- 明言你的假设。若不确，请询。
- 若有多解，皆呈的——勿默择。
- 若有更简的法，言的。必要时质疑。
- 若有不明的处，止的。指困惑的处。询的。

## 2. 简单优先

**以最少代码解问题。勿推测。**

- 勿超所需功能。
- 勿为一次性代码建抽象。
- 勿添未请的"灵活性"或"可配置性"。
- 勿为不可能的场景添错误处理。
- 若你写200行而可成50行，请重写。

问己："高级工程师会言此过复杂乎？"若是，请简化。

- **每文件不应超1000行。** 超1000行的文件致LLM无法一次加载完整上下文，影响代码理解与修改质量。若文件过大，应考虑拆分为多模块或子文件。

## 3. 精准修改

**只改必改的处。只清己的遗留。**

编辑现有代码时：

- 勿"改进"相邻的代码、注释或格式。
- 勿重构无问题的物。
- 匹配现有风格，纵你会用不同方式。
- 若你注意无关的死代码，提及的——勿删的。

当你的更改产生孤立代码时：

- 删你更改致未用的导入/变量/函数。
- 除非被要求，否则勿删预先存在的死代码。

测试标准：每更改的行应直接追溯至用户的请求。

## 4. 目标驱动执行

**定成功标准。循环至验证。**

将任务转换为可验证的目标：

- "添加验证" → "为无效输入编写测试，然后使其通过"
- "修复bug" → "编写重现的测试，然后使其通过"
- "重构X" → "确保前后测试皆通过"

对于多步骤任务，陈述简要计划：

```text
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]
```

强大的成功标准令你可独立循环。弱标准（"使的工作"）需不断澄清。

---

**此准则有效时：** diff中不必要的更改更少，因过度复杂导致的重写更少，澄清问题在实现的前而非在错误的后出现。
