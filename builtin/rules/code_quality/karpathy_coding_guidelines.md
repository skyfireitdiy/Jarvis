# Karpathy 编码行为准则

**核心原则：** 这份准则偏向谨慎而非速度。简单任务请自行判断，不必照单全收。

## 1. 编码前先想清楚

**不要假设，不要藏着困惑，要明说取舍。**

动手实现之前：

- 明确说明你的假设。如果不确定，就问。
- 如果有多个可行方案，把每个都列出来——不要默默挑一个。
- 如果有更简单的做法，直接说。必要时质疑已有的方案。
- 有不清楚的地方就停下来，指出困惑点，向用户确认。

## 2. 保持简单

**用最少的代码解决问题，不做没有根据的猜测。**

- 不做超出需求的额外功能。
- 不为一次性代码引入抽象。
- 不擅自添加没人要求的"灵活性"或"可配置性"。
- 不为不可能出现的场景堆错误处理。
- 如果写了 200 行而 50 行就能完成，请重写。

反问自己："资深工程师会觉得这太复杂吗？"如果是，就简化。

- **每个文件不超过 1000 行。** 超过 1000 行的文件会让模型无法一次性读入完整上下文，影响代码理解与修改质量。文件过大时应拆分为多个模块或子文件。

## 3. 精准修改

**只改该改的地方，只清理你自己留下的问题。**

编辑现有代码时：

- 不要顺手"改进"相邻的代码、注释或格式。
- 不要重构本来没问题的部分。
- 匹配现有的代码风格，即使你自己会写成另一种写法。
- 发现无关的死代码就先提一句，但不要擅自删。

当你的改动产生孤立代码时：

- 删除因你的修改而变得没用的导入、变量或函数。
- 除非被要求，否则不要删除本来就存在的死代码。

测试标准：每一行改动都应该能直接追溯到用户的请求。

## 4. 目标驱动执行

**先定义可验证的成功标准，再循环执行直到验证通过。**

把模糊任务转成可验证的目标：

- "加上校验" → "为无效输入编写测试，然后让测试通过"
- "修 Bug" → "写一个能复现问题的测试，然后让它通过"
- "重构 X" → "确保重构前后相关测试都能通过"

对多步骤任务，先给出简要计划：

```text
1. [步骤] → 验证方式：[如何检查]
2. [步骤] → 验证方式：[如何检查]
3. [步骤] → 验证方式：[如何检查]
```

清晰的成功标准能让你独立地迭代循环。模糊的标准（如"让它能用"）只会让你不断回头澄清。

---

**这套准则什么时候见效：** diff 里不必要的改动更少、因过度设计导致的返工更少、澄清问题发生在动手之前而不是出错之后。
