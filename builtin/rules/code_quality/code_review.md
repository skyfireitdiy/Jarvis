# 代码审查规则

## 汝必审查之方面

### 1. 功能正确性（必验）

**检查项：**

- [ ] 代码是否实现预期功能？
- [ ] 是否处理所有边界情况？
- [ ] 是否处理所有异常情况？
- [ ] 是否有潜在安全漏洞？
- [ ] 是否有明显逻辑错误？

**行动要求：**

- 若发现功能未实现或实现错误，必指出并要求修复
- 若发现缺少边界或异常处理，必要求补充
- 若发现安全漏洞，必标记为阻塞性问题

### 2. 代码质量（必评）

**检查项：**

- [ ] 代码是否清晰易读？
- [ ] 变量与函数命名是否准确有意义？
- [ ] 是否有重复代码需重构？
- [ ] 代码结构是否合理？

**行动要求：**

- 若命名不清晰，必建议更清晰之名
- 若发现重复代码，必建议提取公共逻辑
- 若代码结构混乱，必建议重构

### 3. 性能考虑（必评）

**检查项：**

- [ ] 是否存在明显性能瓶颈？
- [ ] 算法与数据结构选择是否合理？
- [ ] 是否有不必要之计算或资源消耗？
- [ ] 是否有内存泄漏风险？

**行动要求：**

- 若发现性能问题，必指出并提供优化建议
- 若算法选择不当，必建议更合适之方案

### 4. 可维护性（必评）

**检查项：**

- [ ] 代码结构是否合理？
- [ ] 是否遵循项目之编码规范？
- [ ] 是否有适当之注释与文档？
- [ ] 代码是否易于理解与修改？

**行动要求：**

- 若违反编码规范，必要求修正
- 若缺少必要注释，必要求补充
- 若代码难以理解，必要求重构

## 审查行为规范

### 汝必遵守之原则

- **必**：保持建设性反馈，关注代码而非个人
- **必**：提出具体可操作之建议
- **必**：认可良好之实践与设计
- **必**：及时响应审查请求
- **禁**：用攻击性或贬低性之语言

### 审查建议之格式

- 明确指出问题所在（文件、行号、代码片段）
- 说明问题之影响（为何此为问题）
- 提供具体之修复建议（如何修复）
- 若为阻塞性问题，明确标记

### 复杂变更之处理

- 对于大型或复杂之变更，可要求分阶段审查
- 建议将复杂功能拆分为多个小且可审查之提交

## 审查检查清单

完成代码审查时，汝必确认：

**功能层面：**

- [ ] 代码实现预期功能
- [ ] 处理边界与异常情况
- [ ] 无明显 bug 或逻辑错误

**质量层面：**

- [ ] 代码符合项目之编码规范
- [ ] 命名清晰有意义
- [ ] 无重复代码
- [ ] 代码结构合理

**安全与性能：**

- [ ] 无安全漏洞
- [ ] 性能可接受
- [ ] 资源使用合理

**可维护性：**

- [ ] 有适当之错误处理
- [ ] 有必要之测试覆盖
- [ ] 代码注释清晰准确
- [ ] 代码易于理解与维护
