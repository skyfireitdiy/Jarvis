# 新增规则范

## 规则文基本求

### 规则类选择

建规则之前，**必**明确规则之适用范围：

**全局规则 vs 项目规则：**

- **全局规则**：
  - 适用范围：所有项目通用之规则，适用于整个Jarvis系
  - 存放位置：`{{ jarvis_data_dir }}/rules/`录下
  - 典型景：通用码范、安全准、效优略等

- **项目规则**：
  - 适用范围：仅适用于当前项目之特定规则
  - 存放位置：`{{ git_root_dir }}/.jarvis/rules/`录下
  - 典型景：项目特定之构范、开发程、具设等

**选择则：**

1. **通用性优先**：若规则在多个项目中皆能用，应建为全局规则
2. **项目特性优先**：若规则仅针对当前项目之特殊需求，应建为项目规则
3. **维便利**：全局规则需跨项目维，改时需考虑对所有项目之影响
4. **权限考虑**：全局规则通常需更高之权限级别

**作程：**

1. 确定规则类（全局规则或项目规则）
2. 根据类选择对应之文位置（见下方章节）
3. 建规则文
4. 规则会自被索系扫并增至索中

### 1. 文位置（必遵守）

#### 1.1 项目规则文位置

**位置范：**

- **必**：项目规则文应放置于项目之`.jarvis/rules/`录下之对应类子录中

**文径：**

```text
{{ git_root_dir }}/.jarvis/rules/<category>/<rule_name>.md
```

**类释：**

- `<category>`：规则类，议用描述性录名
- **可选参类**（非强制限制）：
  - `architecture_design`（构设）
  - `code_quality`（码质量）
  - `deployment`（布范）
  - `development_tools`（开发具）
  - `development_workflow`（开发程）
  - `performance`（效优）
  - `security`（安全范）
  - `tool_config`（具设）
  - `ui_design`（UI设）
- **可建新之类录**，根据项目实际需求组织规则
- 详细之类选择指南请参本文末尾之「规则类指南」章节

#### 1.2 全局规则文位置

**位置范：**

- **必**：全局规则文应放置于Jarvis数据录之`rules/`录下

**文径：**

```text
{{ jarvis_data_dir }}/rules/<rule_name>.md
```

或按类组织：

```text
{{ jarvis_data_dir }}/rules/<category>/<rule_name>.md
```

**径释：**

- `{{ jarvis_data_dir }}`：Jarvis数据录，通常为`~/.jarvis`或用户设之数据录
- 全局规则文可放置于`rules/`根录下，亦可按类建子录
- 议全局规则亦按照与项目规则相同之类体系组织，便于统一理

### 规则索

**自索机制：**

- Jarvis已现自规则索能，**无需手登**
- 系会自扫`builtin/rules/`和`.jarvis/rules/`录下之所有`.md`文
- 从YAML头部提取`description`域生索
- 索可通过`load_rule`具之内置索能访问

**YAML头部范：**

- **必**：顶层规则文（作为入口之主规则）必含YAML front matter header
- **可选**：子规则文（被顶层规则引用之详细规则）可不含header
- **禁**：header容为空或式误

**对于顶层规则文，所有规则文**必**在文顶部包含YAML头部，式如下：

```yaml
---
name: 规则名 # 必需，规则之简短识
description: 规则能描述 # 必需，规则之详细触发景释
license: MIT # 可选，开源议识
---
```

**域释：**

- **name**（必需）：规则之名识
  - 用于唯一识规则
  - **必**用规则文之简短名（不含.md后缀）
  - **必**用英文或拼音，不议用中文
  - 例：`code_review`, `tdd`, `security`

- **description**（必需）：规则之启条件释
  - 用于规则索展示与自匹
  - **写启条件与不启条件**，不写能介绍、技能释、规则容
  - **必**按照以下详细式编写

- **license**（可选）：开源议识
  - 用于识规则之授权议
  - 常见议：`MIT`, `Apache-2.0`, `GPL-3.0`, `BSD-3-Clause`
  - 若无需特别授权，可不填写此域

**description详细式求：**

```yaml
name: clean_code
description: 若需[明确启条件]时触发。凡用户言及"[启关键词1]"、"[启关键词2]"或[用景]时触发。不启：[明确不启的条件1]；[不启的条件2]；[不启的条件3]。
```

**式要素释：**

1. **启条件**：明确释何种情况下用该规则
   - 式：`若需[具体景]时触发`
   - 例：`若需编写整洁码时触发`

2. **启关键词**：具体之启关键词，用引号括起
   - 式：`凡用户言及"[关键词1]"、"[关键词2]"`
   - 例：`凡用户言及"整洁码"、"码范"、"佳践"`

3. **不启条件**：明确释何种情况下**不**应触发该规则
   - 式：`不启：[条件1]；[条件2]；[条件3]`
   - 例：`不启：仅阅读码不改；仅行测；讨论编程概念但不涉及码编写`

**完整例：**

```yaml
---
name: clean_code
description: 若需编写或审整洁码时触发。凡用户言及"整洁码"、"码范"、"佳践"、"码审"、"可读性"或需要编写/审高质量码时触发。不启：仅阅读码不改；仅行测；讨论编程概念但不涉及码编写。
license: MIT
---
```

**编写则：**

- **必**：包含启条件、启关键词、不启条件三个要素
- **必**：启关键词至少3-5个，用引号括起
- **必**：不启条件至少2-3项，用分号分隔
- **必**：明确触发与不启之边界
- **禁**：在description中写能介绍、技能释、规则容
- **禁**：过于简短或模糊之描述
- **议**：总长度在80-200字之间

**容性释：**

- 系容没有YAML头部之规则文（主要是子规则文）
- 若规则文缺少YAML头部，索将用文名作为描述
- **议**：顶层规则文务必包含完整范之YAML头部，以获得佳索与匹效

### 2. 文命名范（必遵守）

**命名规则：**

- **必**：用小写字母
- **必**：用下划线`_`分隔单词
- **必**：用`.md`后缀
- **禁**：用空格、连字符`-`或大写字母

**命名例：**

- ✅ 正确：`code_review.md`, `tdd.md`, `security.md`
- ❌ 误：`CodeReview.md`, `code-review.md`, `CODE_REVIEW.md`

**命名议：**

- 用简短、描述性之名
- 反映规则之核心用
- 避免过于通用之名（如`rule.md`）

### 3. 规则类（必遵守）

**类体系：**

规则文应放置于合适之类子录中。议根据规则之题与应用景建描述性之类录。以下是常见之类参（**非强制限制，可根据需要建新类**）：

- **architecture_design**（构设）：
  - 设式、构则、码组织构等
  - 例如：SOLID则、整洁构、构图生器

- **code_quality**（码质量）：
  - 码范、审准、文求等
  - 例如：码审、文编写、构验

- **deployment**（布范）：
  - 布程、发范、环设等
  - 例如：开源布、版发

- **development_tools**（开发具）：
  - 开发具使用、脚本生、具设等
  - 例如：脚本生专家

- **development_workflow**（开发程）：
  - 开发法论、工作程、协作程等
  - 例如：TDD、SDD、构程

- **performance**（效优）：
  - 效析、优略、源理等
  - 例如：效优、Rust效优

- **security**（安全范）：
  - 安全码、漏洞析、安全测等
  - 例如：安全码、安全漏洞析

- **tool_config**（具设）：
  - 具设、规则理等
  - 例如：新增规则范、忽警

- **ui_design**（UI设）：
  - 界面设范、题设等
  - 例如：iOS暗色/亮色题

**类选择则：**

1. **单一职责**：每个规则只属于一个类
2. **核心题**：选择规则最核心之题对应之类
3. **避免歧义**：若规则涉及多个领域，选择最主要之应用景
4. **参现有**：优先参`builtin_rules.md`中同类规则所在之类

**例：**

- ✅ `code_review.md` → `code_quality/`（核心是码质量审）
- ✅ `sdd.md` → `development_workflow/`（核心是开发程）
- ✅ `security.md` → `security/`（核心是安全范）

### 4. 文式求（必遵守）

**Markdown式：**

- **必**：用Markdown式
- **必**：用UTF-8码
- **必**：用LF换行符（Unix风格）

**构求：**

```markdown
# 规则标题

## 简/景

（可选）简要释规则之用与景

## 汝必守之则

（必需）规则之核心则

### 具体求1

**求释：**

- **必**：具体求
- **禁**：禁止事项

## 汝必行之作

（必需）具体之行步或范

## 验清单

（可选）完后之证项

- [ ] 验项1
- [ ] 验项2
```

### 4. 容编写求（必遵守）

**语言风格：**

- **必**：用清晰、简洁之语言
- **必**：用肯定式表述（"必"、"禁"）
- **必**：避免模糊之表达

**构化求：**

- 用分级标题组织容（`#`、`##`、`###`）
- 用列罗列求（`-`或`1.`）
- 用码块提供例
- 用加粗强调关键词（`**必**`、`**禁**`）

**完整性求：**

- 释规则之用景
- 提供具体之例码
- 列出必遵守之求
- 列出禁止之事项
- 提供证或验清单

## Jinja2变使用指南

### 可用之内置变

规则文中可用以下Jinja2模变：

| 变名                                       | 释                 | 例值                   |
| -------------------------------------------- | -------------------- | ------------------------ |
| `{% raw %}{{ rule_file_dir }}{% endraw %}`   | 当前规则文所在录 | `/path/to/builtin/rules` |
| `{% raw %}{{ git_root_dir }}{% endraw %}`    | Git仓库根录       | `/home/user/project`     |
| `{% raw %}{{ current_dir }}{% endraw %}`     | 当前工作录         | `/home/user/project/src` |
| `{% raw %}{{ jarvis_src_dir }}{% endraw %}`  | Jarvis源码录      | `/home/user/jarvis`      |
| `{% raw %}{{ jarvis_data_dir }}{% endraw %}` | Jarvis数据录      | `/home/user/.jarvis`     |

### 使用则

- **必**：尽量用jinja2变替代绝对径
- **必**：优先用合适之内置变（如`{% raw %}{{ git_root_dir }}{% endraw %}`、`{% raw %}{{ jarvis_data_dir }}{% endraw %}`等）
- **禁**：在规则文中硬码绝对径（如`/home/user/project`）
- **禁**：用相对径（如`../rules/`）而不用变

**佳践：**

- 项目径用`{% raw %}{{ git_root_dir }}{% endraw %}`
- 数据录用`{% raw %}{{ jarvis_data_dir }}{% endraw %}`
- 当前规则录用`{% raw %}{{ rule_file_dir }}{% endraw %}`

**⚠️ 重要提示：**

`{% raw %}{{ rule_file_dir }}{% endraw %}`变表示**当前规则文所在录**之绝对径。使用时请慎：

- **引用同录下之文**：直接用`{% raw %}{{ rule_file_dir }}{% endraw %}/文名.md`，**勿**重复增录层级
- **误例**：若规则文在`builtin/rules/development_workflow/`录下，引用同录之子规则时，**误**写法是`{{ rule_file_dir }}/development_workflow/sub_rule.md`
- **正确例**：直接写`{{ rule_file_dir }}/sub_rule.md`即可
- **常见误**：因`rule_file_dir`已包含完整之录径（如`/path/to/builtin/rules/development_workflow/`），故不应再增录前缀

### 变使用例

#### 例1：引用其他规则文

```markdown
## 关规则

- 参码审规则：`{% raw %}{{ rule_file_dir }}{% endraw %}/../code_quality/code_review.md`
- 参安全规则：`{% raw %}{{ rule_file_dir }}{% endraw %}/../security/security.md`
```

#### 例2：指定项目径

```markdown
### 文放置位置

**测文必放置于：**

- `{% raw %}{{ git_root_dir }}{% endraw %}/tests/`
- `{% raw %}{{ git_root_dir }}{% endraw %}/src/{% raw %}{{ module_name }}{% endraw %}/tests/`
```

#### 例3：用条件逻辑

```markdown
{% if git_root_dir == current_dir %}
**慎**：当前在项目根录
{% else %}
**慎**：当前在子录中
{% endif %}
```

## 规则模

以下是一个完整之规则文模，可直接复使用：

````markdown
# [规则名]

## 规则简

简要描述规则之用、用景与预期效。

## 汝必守之则

### 1. 则名

**求释：**

- **必**：具体求1
- **必**：具体求2
- **禁**：禁止事项

**例：**

    ```python
    # 例码
    def example():
        pass
    ```

## 汝必行之作

### 作1：作名

**行步：**

1. 步1
2. 步2
3. 步3

**慎事项：**

- 慎事项1
- 慎事项2

## 验清单

完任务后，汝必认：

- [ ] 规则文已建于`{% raw %}{{ git_root_dir }}{% endraw %}/.jarvis/rules/`录
- [ ] 文命名符合范（小写、下划线分隔、.md后缀）
- [ ] 文包含YAML头部，包含`description`域
- [ ] 文放置于合适之类子录中
- [ ] 文式符合Markdown范

## 关源

- 参文：`related_rule.md`
````

## 配套脚本范

建规则时，若规则涉及需自化行之辅助作，可同时建与之配套之脚本文。

### 何时建配套脚本

**议建配套脚本之景：**

- 规则需行重复性之复杂作
- 规则涉及文生、转或批量理
- 规则需与其他具或系集成
- 规则之证需自化验

**可选之景：**

- 简单之单次作（直接内联至规则中即可）
- 纯文性质之规则（无需脚本）

### 脚本命名范

- **必**：用与规则文相同之基础名
- **必**：脚本扩名应反映其语言/类（如`.sh`、`.py`、`.ps1`）
- **必**：用小写字母与下划线

**命名例：**

| 规则文             | 配套脚本              |
| -------------------- | --------------------- |
| `code_review.md`     | `code_review.sh`      |
| `deploy_helper.md`   | `deploy_helper.py`    |
| `batch_processor.md` | `batch_processor.ps1` |

### 脚本位置范

**项目规则配套脚本：**

```text
{{ git_root_dir }}/.jarvis/rules/<category>/scripts/<script_name>.<ext>
```

**全局规则配套脚本：**

```text
{{ jarvis_data_dir }}/rules/<category>/scripts/<script_name>.<ext>
```

**脚本录构例：**

```text
.jarvis/rules/
└── code_quality/
    ├── code_review.md          # 规则文
    └── scripts/
        ├── code_review.sh      # 配套脚本
        └── requirements.txt    # 脚本依赖（可选）
```

### 脚本与规则之关联

#### 1. 在规则中引用脚本

在规则文之适当位置引用配套脚本，例如：

````markdown
### 自化具

本规则配套之自化脚本位于：`{% raw %}{{ rule_file_dir }}{% endraw %}/scripts/code_review.sh`

**使用方式：**

```bash
./scripts/code_review.sh --path ./src --output report.md
```
````

#### 2. 脚本头注释

议在脚本开头增规则关联释：

```bash
#!/bin/bash
#===============================================================================
# 规则关联: code_review.md
# 释: 码审规则之自化行脚本
# 位置: .jarvis/rules/code_quality/scripts/code_review.sh
#===============================================================================
```

### 脚本开发求

**必遵守：**

- **可行性**：脚本必为可行（设置正确之文权限）
- **独立性**：脚本应尽量独立，不依赖未在项目中声明之具
- **文化**：增足够之注释释脚本用与使用法
- **误理**：脚本应包含基本之误理与出码

**议遵守：**

- 增`--help`或`-h`项示使用释
- 支持设文或命令行参
- 录详细志便于排查问题

### 脚本依赖理

若脚本有外部依赖，议在脚本录增依赖释文：

**依赖文命名：**

- Python: `requirements.txt`
- Node.js: `package.json`
- 通用: `DEPENDENCIES.md`

**例`DEPENDENCIES.md`：**

````markdown
# 脚本依赖释

## code_review.sh

### 必需具

- `shellcheck`: 码验
- `git`: Git作

### 可选具

- `fd`: 文寻（未安装时用`find`替代）

## 安装方式

```bash
# Ubuntu/Debian
sudo apt install shellcheck fd

# macOS
brew install shellcheck fd
```
````

## 佳践

### 1. 规则设则

- **单一职责**：每个规则只关注一个题
- **可作性**：规则必具体、可行
- **可证**：规则结果必可验
- **简洁明了**：避免冗长与重复

### 2. 常见误

- ❌ **规则过于抽**："码要写得好看"
- ✅ **规则具体明确**："函长度不超过50行"

- ❌ **规则相互冲突**：规则A求X，规则B求非X
- ✅ **规则协调一致**：关规则应相互补充

- ❌ **缺少例**：只有文字描述，没有例码
- ✅ **提供例**：包含正面与反面之例

### 3. 规则维

- 定期审规则之适用性
- 根据项目发展更规则
- 删过时或不再使用之规则
- 录规则变史

## 附录：规则类指南

### 类决策树

以下决策树可助汝快速确定规则应属于哪个类：

```text
开始
  │
  ├─ 是否关于系构、设式或码组织？
  │   └─ 是 → architecture_design
  │
  ├─ 是否关于码质量、码范或审？
  │   └─ 是 → code_quality
  │
  ├─ 是否关于安全码、漏洞析或安全测？
  │   └─ 是 → security
  │
  ├─ 是否关于效析、优或源理？
  │   └─ 是 → performance
  │
  ├─ 是否关于布、发或环设？
  │   └─ 是 → deployment
```

- 整洁构范
- 码反向设范
- 构图生器设

**典型规则例：**

- 码审范
- 文编写求
- 构验准
