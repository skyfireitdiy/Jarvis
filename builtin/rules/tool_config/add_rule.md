# 新增与管理规则规范

当用户要求新建规则、修改规则体系或规范现有规则时，按本规范执行：确定适用范围、选好存放位置、按统一结构书写规则文件。

## 1. 先确定适用范围：全局规则 vs 项目规则

- **全局规则**：适用于所有项目（通用编码规范、安全基线、性能策略等）。
  - 存放位置：`{% raw %}{{ jarvis_data_dir }}{% endraw %}/rules/` 下，可直接放根目录或按类别建子目录。
- **项目规则**：仅适用于当前项目（项目特定的架构约定、开发流程、工具设置等）。
  - 存放位置：`{% raw %}{{ git_root_dir }}{% endraw %}/.jarvis/rules/<category>/<rule_name>.md`。

**选择原则**：
1. 多个项目都通用 → 建为全局规则；
2. 只针对当前项目 → 建为项目规则；
3. 维护成本：全局规则改动影响所有项目，需谨慎；
4. 权限：全局规则通常需要更高权限（数据目录属用户私有，项目规则随仓库走）。

**流程**：确定类型 → 放到对应路径 → 创建规则文件。文件创建后会被自动扫描进索引，无需手动登记。

## 2. 规则文件结构

```markdown
# 规则标题

## 规则简介
（可选）一句话说明本规则做什么、何时用、预期效果。

## 你必须遵守的原则
（必需）本规则要求的核心原则。每条用一段说明：
- **必须**：具体要做的要求
- **禁止**：明确禁止的事项
可以分多个小节给出多条原则。

## 你必须执行的操作
（必需）本规则要求的具体操作步骤或流程。按阶段/步骤分节，步骤要可执行、可验证。

## 实践指导
（可选）最佳实践、常见错误、注意事项。

## 自检清单
（可选）完成后逐项验证用的清单：
- [ ] 检查项 1
- [ ] 检查项 2
```

> 上面这几个章节名（规则简介 / 你必须遵守的原则 / 你必须执行的操作）是 rule 与方法论统一约定，务必照此书写，避免结构对不上。

## 3. YAML 头（入口规则必填）

放在文件顶部：

```yaml
---
name: code_review        # 必填：规则名，须等于文件名（不含 .md），英文或拼音、小写
description: 触发说明    # 必填：用于索引与自动匹配
license: MIT             # 可选：开源许可标识
---
```

- **name**：用小写英文/拼音，须与文件名一致（如 `security.md` 的 name 是 `security`）。
- **description**：写给规则匹配器看的"触发条件"，不是功能简介。**必须写成"触发/不触发"形式**：
  ```text
  若需[明确场景]时触发。凡用户言及"[关键词1]"、"[关键词2]"或[场景]时触发。不触发：[无关条件1]；[无关条件2]；[无关条件3]。
  ```
  编写要点：
  - 必须包含触发场景、2~5 个带引号的关键词、2~3 条不触发条件；
  - 只描述"什么时候该用"，不要写功能介绍、技能说明或规则正文；
  - 避免过短或含糊；建议总长 80~200 字。
- **license**（可选）：`MIT` / `Apache-2.0` / `GPL-3.0` / `BSD-3-Clause` 等；不涉及授权可不填。

子规则（被顶层规则引用的参考文件）可以没有 YAML 头；缺少头时索引会用文件名代替描述。

## 4. 文件名规范

- 小写字母、下划线分隔、`.md` 结尾；
- 不用空格、连字符或大写。
- 示例：✅ `code_review.md`、`tdd.md`；❌ `CodeReview.md`、`code-review.md`。
- 名字要简短且能说明用途，避免过于通用（如 `rule.md`）。

## 5. 按类别归档

规则放在按主题命名的子目录里。常见类别（非强制，可按需新建）：

| 类别目录 | 覆盖内容 |
| --- | --- |
| `architecture_design` | 架构/设计模式/代码组织 |
| `code_quality` | 代码规范/审查/文档/构建校验 |
| `deployment` | 部署/发布/环境/CI-CD |
| `development_tools` | 工具使用/脚本生成/工具配置 |
| `development_workflow` | 方法论/开发流程/协作（如 TDD、SDD、重构） |
| `performance` | 性能分析/优化/资源管理 |
| `security` | 安全编码/漏洞分析/安全测试 |
| `tool_config` | 工具与规则体系配置（如本文件） |
| `ui_design` | 界面规范/主题设计 |

选择类别：每个规则只归一类，按它最核心的主题归类；拿不准就参照同类内置规则所在的目录。

## 6. Jinja2 模板变量

规则文件支持 Jinja2，可用下列变量写出相对路径，**不要硬编码绝对路径**：

| 变量 | 含义 |
| --- | --- |
| `{% raw %}{{ rule_file_dir }}{% endraw %}` | 本规则文件所在目录（绝对路径） |
| `{% raw %}{{ git_root_dir }}{% endraw %}` | Git 仓库根目录 |
| `{% raw %}{{ current_dir }}{% endraw %}` | 当前工作目录 |
| `{% raw %}{{ jarvis_src_dir }}{% endraw %}` | Jarvis 源码目录 |
| `{% raw %}{{ jarvis_data_dir }}{% endraw %}` | Jarvis 数据目录（通常 `~/.jarvis`） |

使用要点：
- 引用同目录下的子规则：直接写 `{% raw %}{{ rule_file_dir }}{% endraw %}/sub_rule.md`，**不要**再加一层重复的类别前缀；
- 指定项目内位置用 `{% raw %}{{ git_root_dir }}{% endraw %}`，数据位置用 `{% raw %}{{ jarvis_data_dir }}{% endraw %}`；
- 在规则正文里引用这些变量即可；需要展示"字面量 {{ ... }}"时用 `{% raw %}...{% endraw %}` 包裹，避免被当模板解析。

## 7. 配套脚本（按需）

若规则需要自动化辅助操作，可放配套脚本，命名与规则同名、语言用扩展名区分（如 `code_review.md` ↔ `scripts/code_review.py`）。

- 位置：项目 `{% raw %}{{ git_root_dir }}{% endraw %}/.jarvis/rules/<category>/scripts/`，全局 `{% raw %}{{ jarvis_data_dir }}{% endraw %}/rules/<category>/scripts/`。
- 在规则中引用时用变量路径，例如：`{% raw %}{{ rule_file_dir }}{% endraw %}/scripts/code_review.sh`。
- 脚本要可执行、尽量独立、含错误处理；外部依赖可在同目录放 `requirements.txt` / `package.json` / `DEPENDENCIES.md` 说明。

## 8. 最佳实践与维护

**设计规则时**
- 单一职责：一条规则只关注一个主题；
- 可操作：写得具体能执行，避免空话（对比：❌"代码要写好" vs ✅"函数体不超过 50 行"）；
- 可验证：给出明确验收/检查项；
- 相互一致：相邻规则不要互相冲突。

**常见错误**
- 规则写得过于抽象、没有示例；
- 缺少 YAML 头或 description 没写成触发/不触发形式；
- 规则间冲突；
- 硬编码绝对路径。

**维护**
- 定期复查规则的适用性，随项目演进更新；
- 删除过时或不再使用的规则；
- 需要时记录规则变更。
