# C/C++2Rust 转译规则

## 规则简介

用于指导 C/C++ 到 Rust 之代码转译，保转译质量、功能一致与类型安全。此规涵盖规划、实现、构建、审查、优化至评估之完整流程。

⚠

**所支语言特性：**

- **C 语言**：函数、结构体、联合体、枚举、指针、数组等
- **C++ 语言**：类、模板、命名空间、STL容器、智能指针、继承、多态、运算符重载等

## 汝必守之则

### 1. 任务管理之则（核心）

**要旨：**

- **必**：每函数之转译，皆须用 `task_list_manager` 以管其任
- **必**：转译之先，须建任务列，规诸任（规划、实现、构建、审查、优化、评估）
- **必**：用 task_list_manager 之 `add_tasks` 操，添诸子任
- **必**：依依赖关系设任务依赖（如：实现阶段依赖规划阶段）
- **禁**：跳过 task_list_manager，直行任务

**多层任务列之要：**

C/C++ 至 Rust 转译，流程繁复，须据转译规模立不同层级之任务列：

1. **目录级任务列**（按需）
   - **何时需**：转译整目录或多相关目录时
   - **任务内容**：规目录结构、模块组织、依赖关系等
   - **子任务**：含该目录下所有文件之转译任务
   - **示例**：转译 `src/utils/` 下所有 C/C++ 文件（`.c`, `.cpp`, `.h`, `.hpp`）

2. **文件级任务列**（按需）
   - **何时需**：转译单文件或多相关函数/类时
   - **任务内容**：规文件模块位置、函数/类分组、共享类型定义等
   - **子任务**：含该文件中所有函数/类之转译任务
   - **示例**：
     - C：转译 `hash.c` 中所有哈希相关函数
     - C++：转译 `vector.hpp` 中之 `Vector` 类及其成员函数

3. **函数/类级任务列**（必）
   - **何时需**：转译单函数或类时（此乃最小粒度，必建）
   - **任务内容**：规函数/类签名、实现策略、测试用例等
   - **子任务**：含该函数/类之规划、实现、构建、审查、优化、评估阶段
   - **示例**：
     - C：转译单函数 `calculate_hash`
     - C++：转译单类 `String` 及其所有成员函数

**任务列层级关系：**

- 目录级任务列 → 文件级任务列 → 函数级任务列
- 上级任务列之子任务可为下级任务列
- 若只转译单函数，只需建函数级任务列
- 若转译多函数而属同一文件，可建文件级任务列，含多函数级子任务
- 若转译多文件，可建目录级任务列，含多文件级子任务

**任务列之要：**

- 任务类型：复杂任务用 `sub` 型，简单任务用 `main` 型
- 任务描述：每任务必含约束条件、必要求、禁事项、验证标准
- 预期输出：必用结构化格式列预期输出
- 验证方法：任务完成后必供验证方法说明
- **C/C++ 代码位置信息**：**必**于每子任务中含原始 C/C++ 代码之行号位置
  - 函数/类级任务：必含 C/C++ 函数/类所在之文件路径与行号范围
    - C：`path/to/file.c:42-67` 或 `path/to/file.h:10-25`
    - C++：`path/to/file.cpp:42-67` 或 `path/to/file.hpp:10-25`
  - 文件级任务：必含 C/C++ 文件之路径（`.c`, `.cpp`, `.h`, `.hpp`）
  - 目录级任务：必含 C/C++ 目录之路径
  - 位置信息应含于 `background` 字段或 `task_desc` 字段中

### 2. TDD 开发之则

**要旨：**

- **必**：先写测试（#[cfg(test)] mod tests），基于 C/C++ 函数/类行为设计测试用例
- **必**：编写实现使测试通过，确保与 C/C++ 语义等价
- **必**：优化代码，保持测试通过（重构阶段）
- **禁**：无测试而直写实现代码
- **禁**：用 `todo!` 或 `unimplemented!` 为占位符

**C++ 特有之虑：**

- 类之成员函数须分别测公共接口与私有实现（通过公共接口）
- 模板函数/类须测不同模板参数之实例化
- 运算符重载须测所有重载之运算符

**示例：**

```rust
// ❌ 错误：先写实现
pub fn calculate(x: i32) -> i32 {
    x * 2
}

#[cfg(test)]
mod tests {
    #[test]
    fn test_calculate() { }
}
```

```rust
// ✅ 正确：先写测试
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_calculate_normal() {
        assert_eq!(calculate(5), 10);
    }

    #[test]
    fn test_calculate_zero() {
        assert_eq!(calculate(0), 0);
    }
}

pub fn calculate(x: i32) -> i32 {
    x * 2
}
```

### 3. 功能一致之则

**要旨：**

- **必**：核心功能定义与 C/C++ 实现一致（主要目之与预期行为）
- **许**：安全改进致行为不一致（修复缓冲区溢出、空指针解引用等安全漏洞）
- **略**：语言差异致行为不一致（整数溢出处理、未定义行为处理等）
- **许**：用不同之类型设计、错误处理方式、资源管理方式
- **禁**：改核心功能逻辑

**释：** 核心功能指函数/类之主要目之（如"计算哈希值"、"解析字符串"、"管理动态数组"），不含实现细节。

**C++ 特有之虑：**

- 类之封装性：保持公共接口一致，内部实现可不同
- 继承关系：保持继承层次与虚函数行为一致
- 模板实例化：确保模板在不同类型参数下行为一致
- STL 容器：可用 Rust 标准库之等价容器（如 `Vec` 对应 `std::vector`）
- 智能指针：可用 Rust 之所有权系统（`Box`, `Rc`, `Arc`）替代

### 4. 模块化设计之则

**要旨：**

- **必**：按功能内聚与依赖方向选模块，避循环依赖
- **必**：模块路径须位于 crate 之 src/ 目录下
- **必**：优先将函数置于已存之模块中
- **许**：必要时建新子模块文件
- **禁**：将不相关之功能置于同一模块

### 5. 类型安全之则

**要旨：**

- **必**：优先用 Rust 原生类型（i32/u32、&str/String、&[T]/&mut [T]、Result<T,E>）
- **禁**：优先用 C 风格类型（core::ffi::c*、libc::c*）
- **禁**：用 extern "C"（除非 FFI 导出所需）
- **必**：函数签名应循 Rust 最佳实践，无需兼容 C 之数据类型
- **禁**：用 `use ...::*` 通配导入

### 6. 文档记录之则

**要旨：**

- **必**：每转译阶段皆须生成文档记录
- **必**：文档记录应含阶段执行过程、决策依据、所遇问题与解决方案
- **必**：文档记录应含 C 代码位置信息，便于追溯
- **必**：文档记录应用结构化格式（Markdown），便于阅读与维护
- **必**：文档记录应在阶段完成后即生成，确保信息准确完整
- **禁**：跳过文档记录，直入下一阶段

**文档记录之要：**

- 文档格式：用 Markdown 格式
- 文档位置：建议存于 `docs/transpilation/` 目录下，按函数/文件/目录组织
- 文档命名：用清晰之命名规则（如：`function_name_planning.md`、`file_name_implementation.md`）
- 文档内容：必含阶段概述、执行过程、关键决策、问题与解决方案、验证结果
- 文档链接：于任务列表之预期输出中含文档路径

## 汝必行之操作

**要示：** 转译之先，须据转译规模择合适之任务列层级：

- **转译单函数**：建函数级任务列（必）
- **转译单文件或多相关函数**：建文件级任务列，含多函数级子任务（按需）
- **转译整目录或多相关目录**：建目录级任务列，含多文件级子任务（按需）

以下操作阶段适用于所有层级之任务列，然具体执行粒度取决于任务列层级。

### 阶段 1：规划阶段

#### 操作1：记录 C/C++ 代码位置信息

- **必**：记录原始 C/C++ 代码之位置信息
  - 函数/类级：记录 C/C++ 函数/类所在之文件路径与行号范围
    - C：`path/to/file.c:42-67` 或 `path/to/file.h:10-25`
    - C++：`path/to/file.cpp:42-67` 或 `path/to/file.hpp:10-25`
  - 文件级：记录 C/C++ 文件之完整路径（`.c`, `.cpp`, `.h`, `.hpp`）
  - 目录级：记录 C/C++ 目录之路径（如：`path/to/dir/`）
- **必**：将位置信息含于任务描述、背景信息或预期输出中
- **必**：确保位置信息准确，便于后续追溯与验证
- **C++ 特有**：对于模板类/函数，须记录所有实例化之位置

#### 操作2：选模块位置

- 析函数之功能特性，定所属之功能模块
- 检 crate 目录结构，择或建合适之模块文件
- 确保模块路径位于 src/ 目录下
- 评估是否需要建新子模块文件

#### 操作3：设计 Rust 函数/结构体/特征签名

- 据 C/C++ 函数/类签名设计 Rust 函数/结构体/特征签名
- 优先用 Rust 原生类型，避 C/C++ 风格类型
- 考虑用 `Result<T, E>` 或 `Option<T>` 处理错误
- 若为根符号，必用 `pub` 关键字
- **必**：于函数/结构体注释中记录对应之 C/C++ 代码位置信息（如：`/// 转译自 path/to/file.c:42-67`）

**C++ 特有处理：**

- **类转结构体**：C++ 类转 Rust 结构体，成员函数转关联函数或方法
- **继承转特征**：C++ 继承关系转 Rust 特征（trait）与实现（impl）
- **模板转泛型**：C++ 模板转 Rust 泛型（`<T>`）
- **命名空间转模块**：C++ 命名空间转 Rust 模块
- **STL 容器映射**：
  - `std::vector<T>` → `Vec<T>`
  - `std::string` → `String` 或 `&str`
  - `std::map<K, V>` → `std::collections::HashMap<K, V>`
  - `std::unique_ptr<T>` → `Box<T>`
  - `std::shared_ptr<T>` → `Rc<T>` 或 `Arc<T>`
- **运算符重载**：用 Rust 之运算符特征（如 `Add`, `Sub`, `Deref` 等）

#### 操作4：评估是否需要实现

以下情形可跳过实现（设 skip_implementation 为 true）：

- **已实现之函数/类**：函数/类已在目标模块中实现，且功能与 C/C++ 实现一致
- **资源释放类函数**：如 fclose、free、delete 等，通过 RAII 自动管理
- **已被库替代**：函数/类已被标准库或第三方 crate 替代，且功能完全一致
- **空实现或无意义函数**：C/C++ 函数为空实现、简单返回常量
- **内联函数或宏**：在 C/C++ 中为内联函数或宏
- **C++ 特有**：
  - 纯虚函数（若 Rust 特征已定义）
  - 默认构造函数/析构函数（Rust 自动处理）
  - 某些 STL 容器之简单包装（可直接用 Rust 标准库）

**要**：跳过实现须于 notes 字段中详述原因。

- **必**：生成规划阶段文档记录
- **必**：文档含以下内容：
  - C 代码位置信息（文件路径与行号范围）

### 阶段 2：实现阶段

#### 操作1：编写测试用例

- 于 `#[cfg(test)] mod tests { ... }` 块中编写测试
- 测试用例必覆盖：
  - 主要功能路径
  - 边界情形（空输入、极值、边界值）
  - 错误情形（若 C/C++ 实现有错误处理）
- 测试用例之预期结果必与 C/C++ 实现行为一致
- 用清晰之测试名称与适当之断言

**C++ 特有测试之要：**

- **类测试**：测所有公共方法，含构造函数、析构函数、运算符重载
- **继承测试**：测基类与派生类之方法，含虚函数之多态行为
- **模板测试**：测模板在不同类型参数下之行为（如 `Vec<i32>`, `Vec<String>`）
- **异常处理**：C++ 异常转 Rust 之 `Result` 或 `panic`，须相应测试
- **移动语义**：测移动构造函数与移动赋值运算符之等价行为

#### 操作2：实现函数/结构体/特征

- 使测试通过，实现与 C/C++ 语义等价之功能
- 用 Rust 原生类型与惯用法
- 考虑用 RAII 管理资源
- 加中文注释说明逻辑

**C++ 特有实现之要：**

- **类实现**：将 C++ 类转 Rust 结构体，成员变量为字段，成员函数为方法
- **构造函数**：用 `new()` 或 `Default` 特征实现
- **析构函数**：用 `Drop` 特征实现
- **继承**：用特征与实现（`impl Trait for Struct`）模拟继承
- **多态**：用特征对象（`Box<dyn Trait>`）实现运行时多态
- **模板泛型**：用 Rust 泛型实现，考虑用特征约束（`where T: Trait`）
- **运算符重载**：实现相应之运算符特征（如 `Add`, `Sub`, `Mul`, `Deref` 等）
- **智能指针**：
  - `std::unique_ptr<T>` → `Box<T>`
  - `std::shared_ptr<T>` → `Rc<T>`（单线程）或 `Arc<T>`（多线程）
  - `std::weak_ptr<T>` → `Weak<T>`

#### 操作3：重构代码

- 优化代码结构，保持测试通过
- 改进代码可读性与可维护性
- 确保不改功能行为

### 阶段 4：审查阶段

**审查优先级：**

1. **测试破坏性检查**（最高优先级）
   - 检 `#[test]` 标记是否丢失
   - 检 `#[test]` 标记是否重复
   - 检代码插入位置是否破坏测试结构
   - 验证测试仍可运行

2. **严重问题检查**
   - 空指针解引用风险
   - 越界访问问题
   - 会导致 panic 之严重错误

3. **测试用例完备性检查**
   - 是否有测试用例
   - 是否覆盖主要功能
   - 是否覆盖边界情形
   - 是否覆盖错误情形

4. **功能一致性检查**
   - 核心输入输出是否一致
   - 主要功能逻辑是否一致
   - 允许安全改进致行为不一致
   - **C++ 特有**：
     - 类之公共接口是否一致
     - 继承关系是否正确转换
     - 模板实例化行为是否一致
     - 运算符重载行为是否一致

5. **破坏性变更检测**
   - 检查模块导出变更
   - 检查类型定义变更
   - 允许签名不一致（只要功能实现）

6. **文件结构合理性检查**
   - 模块文件位置是否合理
   - 文件命名是否符合规范
   - 模块导出是否正确
