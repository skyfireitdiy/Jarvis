# Jarvis 用户手册编写规则

## 规则简介

本规则用于约束 Jarvis 项目用户手册之编写与修订方式，确保文档真正面向最终用户，而非面向开发者或维护者。
用户手册之核心目标非"概括功能存在"，而在令用户**阅毕即知如何操作**。故所有文档必建于真实源码行为、CLI 参数、交互提示、界面反馈与配置边界之上，禁只据功能标题、草案摘要或主观理解直写正式文档。

## 汝必遵守之原则

### 1. 必先阅读源码与真实交互行为

**要求说明：**

- **必**：先阅相关源码、CLI 入口、交互提示、配置项、前端界面或实际用户可见反馈，再始编正式用户手册。
- **必**：优先确认用户真实可见之提示文案、输入方式、提交方式、成功/失败反馈。
- **必**：区分自动触发、手动触发、条件触发、权限限制等行为。
- **禁**：只据功能标题、功能清单、草案摘要或函数命名推测用户行为。
- **禁**：未确认入口而写"先触发""先启用""调用入口"等模糊步骤。

### 2. 必写成用户可直接操作之指南

**要求说明：**

- **必**：每篇文档尽量令用户可直接照做，而非仅理解概念。
- **必**：操作步骤优先写清以下信息：
  - 用户于何处操作（终端、对话输入框、Web 界面、启动命令等）
  - 用户输入何原样文本
  - 用户按何键或如何提交
  - 系统将示何提示、列表、状态或结果
- **必**：若功能属自动触发，须明写"此乃自动发生，无需额外输入命令"。
- **禁**：以"系统会……"为主要步骤，而不说明用户前置操作。
- **禁**：写用户无法直接执行之自我引用式步骤，如"先查看""先恢复""先触发"而不说明具体做法。

### 3. 必保持面向用户，禁泄露实现细节

**要求说明：**

- **必**：用最终用户能理解之语言描述功能、步骤与结果。
- **必**：用"系统""当前会话""输入框""提示""列表"等用户视角词汇描述行为。
- **禁**：于正式用户手册中暴露函数名、类名、内部调用链、源码文件路径、实现细节。
- **禁**：出现"源码显示""代码里可以看到""据某函数逻辑"等开发者视角表述。
- **禁**：将开发者接口、内部工具调用方式直当普通用户入口，除非源码明确显示此为用户可见入口。

### 4. 必写清边界条件与限制

**要求说明：**

- **必**：对需特定入口、特定配置、特定权限、特定模式方可使用之功能写清边界。
- **必**：明确区分交互模式与非交互模式、CLI 与 Web、自动行为与手动行为。
- **必**：若某命令非所有入口皆可用，须写"若当前入口支持……"。
- **必**：若某能力依赖预先开启之配置，须写"先进入已开启该能力之会话或启动方式"。
- **禁**：默认假设所有启动方式皆支持同一能力。
- **禁**：将仅于任务结束阶段出现之提示，写成普通输入阶段可随时触发之命令。

### 5. 必统一文档结构并保证可验收

**要求说明：**

- **必**：正式用户文档至少含以下部分：
  - 使用场景
  - 操作步骤
  - 效果说明或汝将见之提示与反馈
  - 注意事项
- **必**：文档风格保持统一，标题应描述用户能完成之动作或场景。
- **必**：若为可交互能力，操作步骤中应尽量含真实提示、快捷键、确认方式或输出结果。
- **必**：若为自动能力，效果说明中应含用户可观察之提示、状态或后续影响。
- **禁**：仅概括说明而无用户步骤。
- **禁**：将内部设计说明写成用户手册正文。

## 汝必执行之操作

### 操作1：编写用户手册前先做取证

**执行步骤：**

1. 确认目标功能对应之源码入口、CLI 参数、交互提示、配置行为或前端表现。
2. 记录用户实际可见之输入方式、快捷键、提示语、状态变化与结果。
3. 判断该功能为：手动触发、自动触发、条件触发，或仅于某些入口可用。
4. 唯关键信息确认后，方始编正式文档。
**注意事项：**

- 不明确之行为宁可继续取证，勿凭经验补写。
- 若真实入口尚未确认，优先于文档中写清前提边界，而非编造统一入口。

### 操作2：将功能写成可执行步骤

**执行步骤：**

1. 先写使用场景，说明用户为何会用此功能。
2. 再写操作步骤，优先按"于何处输入 → 输入何物 → 如何提交 → 后续见何物"之序组织。
3. 接着写效果说明或提示反馈，列出用户可能见之真实信息。
4. 最后补注意事项，说明限制、风险、入口差异与适用边界。
**注意事项：**

- 若文档中出现"先查看""先触发""先启用"等词，必继续补足具体动作。
- 若某步骤为跳过、取消、回车、选择编号，亦须写清。

### 操作3：完成后按用户可操作性回查

**执行步骤：**

1. 通读文档，检查用户能否于不看源码之前提下直接照做。
2. 检查是否已写清：输入位置、输入内容、提交方式、反馈提示。
3. 检查是否误写开发者视角内容或内部实现细节。
4. 检查是否遗漏模式差异、权限限制或自动/手动边界。
**注意事项：**

- 若读毕文档，用户仍不知第一步具体如何做，则文档不合格。
- 若文档虽正确但仅停留于概括描述，亦不合格。

## 检查清单

完成用户手册编写或修订后，汝必确认：

- [ ] 文档内容已基于真实源码、CLI、交互提示、前端行为或配置行为取证
- [ ] 文档含"使用场景 / 操作步骤 / 效果说明或提示反馈 / 注意事项"
- [ ] 操作步骤已尽量写清输入位置、原样文本、提交方式与用户可见反馈
- [ ] 自动触发与手动触发已明确区分
- [ ] 权限限制、入口限制、模式差异已写明
- [ ] 文档中未暴露函数名、内部调用链、源码依据字样或其他实现细节
- [ ] 文档从最终用户视角可理解、可执行、可验证
