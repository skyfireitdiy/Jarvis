# edit_file 宽松匹配功能规范

## 1. 功能概述

### 1.1 目标

为 `src/jarvis/jarvis_tools/edit_file.py` 提供自动宽松匹配能力，解决 `search` 文本因空白、缩进或局部内容变化而无法精确命中的问题，同时保持现有工具调用格式不变。

### 1.2 使用场景

作为调用方，我希望在以下场景下仍能完成编辑：

- 目标文本仅存在空格、Tab、换行风格差异；
- 目标代码块整体缩进发生变化；
- 目标文本中间部分有轻微变更，但开头和结尾上下文仍稳定；
- 目标文本与文件内容高度相似但非完全一致。

### 1.3 范围

本规范仅覆盖 `edit_file` 工具内部匹配策略的增强，不改变工具对外参数结构、字段名称或调用方式。

### 1.4 非目标

以下内容不在本次范围内：

- 不新增外部调用参数；
- 不将模糊匹配改为默认无确认自动替换；
- 不引入正则表达式搜索语法；
- 不修改空 `search == ""` 的整文件重写语义。

## 2. 接口定义

### 2.1 对外接口

对外接口保持不变：

```python
execute(args: Dict[str, Any]) -> Dict[str, Any]
```

`args` 中 `files[].diffs[].search` 和 `replace` 的结构保持不变，不新增 `match_mode`、`threshold` 等外部字段。

### 2.2 内部行为接口

系统应在内部对每个非空 `search` 自动执行如下匹配降级顺序：

1. 精确匹配（Exact Match）
2. 方案 A：空白宽松匹配（Whitespace-normalized Match）
3. 方案 B：缩进宽松匹配（Indent-flexible Match）
4. 方案 C：锚点匹配（前 n 行 + 后 n 行）
5. 方案 D：相似匹配（Similarity-based Match）

### 2.3 确认规则

- 精确匹配且唯一命中时，可直接替换；
- 精确匹配存在多处命中时，沿用现有大模型确认逻辑；
- 任何非精确匹配（方案 A/B/C/D）即使唯一命中，也必须先经过大模型确认；
- 未确认通过时，不得应用该次非精确匹配替换。

## 3. 输入输出说明

### 3.1 输入

#### search

- 类型：`str`
- 约束：
  - 允许为空字符串；
  - 为空字符串时表示直接重写整个文件；
  - 非空字符串时进入匹配流程。

#### replace

- 类型：`str`
- 约束：允许为空字符串，表示删除目标文本。

### 3.2 输出

工具整体输出格式保持现有结构不变，包括：

- `success`
- `stdout`
- `stderr`

内部应能够区分：

- 精确匹配成功；
- 非精确匹配成功并已确认；
- 所有匹配策略均失败；
- 命中候选但未通过确认。

### 3.3 错误输出

当编辑失败时，错误信息应明确说明：

- 精确匹配失败；
- 已尝试的宽松匹配策略；
- 是否找到候选但未通过确认；
- 若适用，提示调用方重新读取文件后调整 `search` 文本。

## 4. 功能行为

## 4.1 总体流程

对于每个 diff：

1. 若 `search == ""`，直接用 `replace` 重写整个文件，并跳过后续 diff；
2. 若 `search == replace`，视为无效操作并报错；
3. 对非空 `search`，按以下顺序尝试匹配：
   - Exact
   - A：空白宽松匹配
   - B：缩进宽松匹配
   - C：前 n 行 / 后 n 行锚点匹配
   - D：相似匹配
4. 若某一步得到候选：
   - 若为精确唯一匹配，则直接替换；
   - 若为精确多处匹配，则走现有确认流程；
   - 若为非精确匹配，则必须走大模型确认流程；
5. 若确认通过，则应用替换并继续后续 diff；
6. 若确认不通过，则本 diff 失败，但保留之前已成功的 diff；
7. 若全部策略均失败，则记录失败并继续处理后续 diff。

## 4.2 方案 A：空白宽松匹配

### 目标

在不改变文本语义顺序的前提下，忽略空白差异进行匹配。

### 允许忽略的差异

- `\n` 与 `\r\n` 的换行差异；
- 行尾空白；
- 连续空格与 Tab 的表示差异；
- 行内多个连续空白的标准化差异。

### 约束

- 文本行序必须保持一致；
- 非空白字符序列必须一致；
- 若得到候选，必须进入大模型确认。

## 4.3 方案 B：缩进宽松匹配

### 目标

允许多行文本整体缩进层级不同，但主体内容一致时完成匹配。

### 行为要求

- 主要用于多行文本；
- 允许每行存在统一的前导缩进差异；
- 行顺序必须一致；
- 行内容主体在忽略共同缩进后应一致；
- 若得到候选，必须进入大模型确认。

### 失败条件

- 文本行数不一致；
- 去除缩进后内容仍不一致；
- 存在多个不可区分候选。

## 4.4 方案 C：前 n 行 / 后 n 行锚点匹配

### 目标

当整体文本无法直接匹配时，优先尝试使用 `search` 的前 n 行和后 n 行作为锚点定位目标区域。

### 行为要求

- 仅适用于至少 3 行的多行 `search`；
- 系统应优先尝试前 n 行锚点匹配；
- 若失败，再尝试后 n 行锚点匹配；
- 若前后锚点都能稳定定位到同一候选区域，则可生成候选替换范围；
- 若仅前锚点或仅后锚点能唯一定位，也可作为候选；
- 若得到候选，必须进入大模型确认。

### n 的要求

- `n` 应为内部固定小整数；
- 必须保证对短文本不会越界；
- 当 `search` 总行数不足以构成有效前后锚点时，应跳过方案 C。

## 4.5 方案 D：相似匹配

### 目标

在前述策略均失败时，从文件中寻找与 `search` 高度相似的候选片段。

### 行为要求

- 只作为最后一级降级策略；
- 必须基于明确的相似度阈值；
- 若存在多个候选，应优先选择最优候选；
- 若最优候选不唯一或低于阈值，则视为失败；
- 若得到候选，必须进入大模型确认。

### 安全要求

- 相似匹配不得在未确认情况下自动应用；
- 若候选差异过大，应拒绝替换。

## 5. 边界条件

### 5.1 空 search

- `search == ""` 时，继续保留整文件重写行为；
- 若第一个 diff 的 `search == ""`，后续 diff 不再执行。

### 5.2 单行文本

- 单行文本通常不适用方案 C；
- 单行文本可尝试 Exact、A、D；
- 若 B 无实际意义，可直接跳过。

### 5.3 多处候选

- 任一策略若得到多个候选，必须采取保守策略；
- 精确多处匹配沿用现有确认逻辑；
- 非精确多候选只有在系统能明确生成单一替换结果且通过确认时才可继续，否则失败。

### 5.4 已有部分成功修改

- 若前面的 diff 已成功，后续某个 diff 失败，不回滚之前成功的 diff；
- 文件整体结果可表现为部分成功，与现有行为保持一致。

### 5.5 文件被外部修改

- 若文件内容与调用方预期不一致，所有策略都可能失败；
- 错误信息应提示重新读取文件内容后再构造 `search`。

## 6. 异常处理

### 6.1 参数异常

- `search` 缺失或不是字符串：返回参数错误；
- `replace` 缺失或不是字符串：返回参数错误。

### 6.2 匹配异常

- 所有匹配策略均失败：返回未找到可接受匹配；
- 找到非精确候选但确认未通过：返回已取消或未确认；
- 匹配过程内部异常：返回失败并保守处理，不进行替换。

### 6.3 写入异常

- 写回文件失败时，继续沿用现有回滚策略，恢复备份文件。

## 7. 验收标准

### AC-1 精确匹配兼容性

当 `search` 在文件中唯一精确命中时，系统必须直接完成替换，行为与当前版本一致。

### AC-2 空白宽松匹配

当 `search` 与目标文本仅存在空格、Tab 或换行风格差异时，系统必须能在 Exact 失败后通过方案 A 找到候选，并在大模型确认通过后完成替换。

### AC-3 缩进宽松匹配

当多行目标文本仅存在整体缩进差异时，系统必须能在方案 B 找到候选，并在确认通过后完成替换。

### AC-4 锚点匹配

当 `search` 中间部分有变化，但前 n 行或后 n 行仍可稳定定位目标区域时，系统必须能通过方案 C 生成候选，并在确认通过后完成替换。

### AC-5 相似匹配

当 A/B/C 全部失败，但文件中存在单一高相似度候选时，系统必须能通过方案 D 给出候选，并在确认通过后完成替换。

### AC-6 非精确匹配确认要求

所有 A/B/C/D 命中的候选，即使唯一命中，也必须经过大模型确认；若未确认通过，不得修改文件。

### AC-7 精确多处匹配兼容性

当 `search` 精确命中多处时，系统必须继续沿用现有大模型确认机制。

### AC-8 失败信息可诊断

当所有匹配策略均失败时，错误信息必须说明已尝试的匹配阶段，并给出重新读取文件内容的建议。

### AC-9 外部接口不变

实现后，`edit_file` 工具的 JSON schema、入参字段和调用方式必须保持不变。

### AC-10 空 search 语义不变

`search == ""` 的整文件重写行为必须保持不变。

## 8. 验证方法

### 8.1 文档验证

- Spec 文件位于 `.jarvis/rules/spec/`；
- 文件名为小写下划线命名；
- 含 YAML 头部；
- 内容包含功能概述、接口定义、输入输出、功能行为、边界条件、异常处理、验收标准。

### 8.2 实现验证

至少覆盖以下测试场景：

1. 精确唯一匹配成功；
2. 精确多处匹配触发确认；
3. 空白差异命中方案 A 并触发确认；
4. 缩进差异命中方案 B 并触发确认；
5. 前 n 行 / 后 n 行锚点命中方案 C 并触发确认；
6. 高相似度命中方案 D 并触发确认；
7. 所有策略失败时返回清晰错误；
8. `search == ""` 时整文件重写行为不变。

## 9. 示例

### 示例 1：空白宽松匹配

调用方提供的 `search` 与文件内容仅换行风格不同，系统应在 Exact 失败后通过方案 A 找到候选，并要求确认。

### 示例 2：缩进宽松匹配

调用方提供的代码块未包含实际文件中的额外缩进，系统应在方案 B 中识别为同一代码块，并要求确认。

### 示例 3：锚点匹配

调用方提供的多行代码块中间部分已被小幅改写，但前两行和后两行仍可定位原区域，系统应通过方案 C 产生候选，并要求确认。

### 示例 4：相似匹配

调用方提供的 `search` 与文件中现有片段高度相似但不完全一致，系统仅在 A/B/C 失败后通过方案 D 给出候选，并要求确认。
